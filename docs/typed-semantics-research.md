# Typed primitive semantics research

Reference: original Blitz3D source at `/tmp/blitz-research/blitz3d`, commit `6beb288`. This is source inspection, not an executable differential. The tree has Windows project files and Windows-only runtime includes; no compiler executable is present. `dotnet` and `wine` are not available in PATH, so running this reference was not feasible without building/installing tooling. Claims below are labeled as implementation evidence; behavior that depends on a platform/runtime is called out.

## Conversion rules and typing

- `Type::canCastTo` permits every conversion among int, float, and string (`compiler/type.cpp:11-36`). `ExprNode::castTo` enforces that gate, and `CastNode::semant` folds constants by asking the constant node for the target representation (`compiler/exprnode.cpp:11-35`). Thus the source supports both implicit casts (assignment/arguments/operators) and the explicit `Int`, `Float`, and `Str` builtins; they share the same cast machinery. Explicit builtin parse cases are in `compiler/parser.cpp:620-633`.
- Runtime casts are distinct paths: float→int and int→float become numeric codegen operations; string→int uses `__bbStrToInt`; int→string uses `__bbStrFromInt`; string→float and float→string similarly use their runtime helpers (`compiler/exprnode.cpp:41-71`).
- Integer constants cast to int unchanged; float constants cast to int through `FloatConstNode::intValue`, which sets x87 round-to-nearest and 24-bit precision, then `fistp` (`compiler/exprnode.cpp:237-247`). Runtime float→int emits x87 `fistp` with no local rounding-mode setup (`compiler/codegen_x86/codegen_x86.cpp:393-397`). Therefore constant and runtime conversion are not demonstrably equivalent if the active x87 control word differs; at least ties use nearest-even for the constant path. Do not substitute a language-default cast until the target policy is explicitly selected and verified.
- String constants parse with C `atoi` / `atof` (`compiler/exprnode.cpp:270-277`); runtime parsing uses the same functions (`bbruntime/basic.cpp:145-157`). That implies C-library prefix parsing and zero for no recognized prefix, subject to platform behavior. Runtime float parse narrows the `double` result of `atof` to `float`.
- Constant int→string uses `itoa`; runtime int→string also uses `itoa` (`compiler/exprnode.cpp:222-224`, `bbruntime/basic.cpp:150-152`). Constant float→string uses `ftoa`; runtime float→string uses the same helper (`compiler/exprnode.cpp:253-255`, `bbruntime/basic.cpp:159-161`). The helper formats 6 significant digits, uses exponent notation outside its range, strips trailing zeroes, and spells special values `NaN`, `Infinity`, `-Infinity` (`stdutil/stdutil.cpp:187-246`). Source evidence indicates matching pathways; no executable comparison was made.
- Suffix tags `%`, `#`, `$` resolve to int, float, string respectively (`compiler/environ.cpp:44-47`); declarations without a tag default to int (`compiler/declnode.cpp:55-59`; implicit identifiers likewise default int at `compiler/varnode.cpp:51-65`). Explicit use of a mismatched suffix on an already declared variable is rejected (`compiler/varnode.cpp:58-61`). Suffixes on function calls are return-type assertions (`compiler/exprnode.cpp:148-157`). The tokens are parsed separately following identifiers/calls (`compiler/parser.cpp:369-380`, `383-400`).

## Operators, initialization, and representation

- Arithmetic promotion: if either operand is string, only `+` is legal and both operands cast to string (concatenation); otherwise `^` or either float operand promotes both operands to float; otherwise both are int (`compiler/exprnode.cpp:371-389`). String concatenation lowers to `__bbStrConcat` (`compiler/exprnode.cpp:424-429`). This means numeric-plus-string is string concatenation after formatting the numeric value, not numeric parsing.
- Uninitialized locals are initialized to numeric zero by `createVars`; string variables use a null pointer representation and load as an empty string through `_bbStrLoad` (`compiler/node.cpp:66-81`, `compiler/varnode.cpp:8-18`, `bbruntime/basic.cpp:124-126`). Globals receive a zero data word (`compiler/declnode.cpp:86-91`, also type fields at `:278-280`); zero pointer likewise loads as empty string. This behavior is visible for strings, not just numeric slots.
- Primitive float representation is C++ `float` in constants and runtime helpers (`compiler/exprnode.cpp:229-255`, `bbruntime/basic.cpp:154-160`); target x86 evaluation uses the x87 FP stack (`compiler/codegen_x86/codegen_x86.cpp:427-453`). The compiler explicitly requests x87 24-bit precision only for compile-time float-to-int conversion. Runtime operation rounding/extended intermediates depend on generated x86/x87 state; no executable confirmation was possible.
- Constant division-by-zero is diagnosed at compile time for literal/folded right operands (`compiler/exprnode.cpp:390-395`). Runtime integer division emits x86 `idiv` (`compiler/codegen_x86/codegen_x86.cpp:142-146`); runtime float division emits x87 `fdivp/fdivrp` (`:219-225`). Runtime divide-by-zero behavior is therefore platform exception/FPU-state dependent in this source and must not be mapped to a guessed C# exception/IEEE result without compatibility tests.

## Compatibility guidance and open points

Implement conversions through explicit compatibility helpers. Preserve the int/float/string promotion rules and suffix checks. Use a single known formatter/parser only after its edge behavior is tested against the intended Blitz version; the source's `atoi`/`atof`, 32-bit `int`, custom six-significant-digit formatter, and x87 conversion path carry platform assumptions. In particular, tests should discriminate float→int ties and negative fractions, malformed/prefix numeric strings, float formatting near exponent thresholds and special values, string-concat promotion, and division by zero. Those are validation recommendations, not results of an executable differential.

Evidence limits: inspection did not establish the initial runtime x87 control word, non-finite float-to-int behavior, C locale effects, integer overflow behavior, or exact runtime division traps. The checkout's compiler source is Windows-centric and could not be run in this environment.
